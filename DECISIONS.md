# Decisions log

Interview script — every real choice, why it was made. See `CLAUDE.md` Rule 4.

| # | decision | tried / alternatives | why kept |
|---|---|---|---|
| 1 | Primary eval set: T²-RAGBench (`G4KMU/t2-ragbench`), not FinanceBench | FinanceBench claims 10,231 triples; only 150 public (rest gated). T²-RAGBench: 23,088 rows / 7,318 docs, fully open, confirmed loads (`dataset.py`) | 150 examples too small to gate CI on (§2.3: ~4pt stderr at n=150). FinanceBench kept as secondary sanity check only |
| 2 | ConvFinQA split: 80/10/10 by document, seed 42 | Ships with no split (`split=="all"`, 3,458 rows). FinQA is 75.5/13.9/10.7, TAT-DQA 79.9/10.1/10.1 by row — no exact ratio to copy | 80/10/10 matches TAT-DQA + convention. Grouped by `context_id` (not row) to stop the ~1.9 questions/doc from leaking a document across splits. Actual: 78.3/11.5/10.2 by row, zero cross-split docs. `assign_convfinqa_splits()` in `dataset.py` |
| 3 | Store: Postgres + pgvector, not a dedicated vector DB (Pinecone/Weaviate/Qdrant) | Dedicated vector DBs win at scale (native horizontal sharding, ANN-only specialization) for hundreds of millions+ vectors | Our corpus is ~23k rows / ~100k chunks — HNSW in pgvector handles that on one instance easily. We also need hybrid search (dense + BM25 + relational metadata) — one Postgres transaction vs. 2-3 separate systems + consistency glue. Not a claim pgvector matches dedicated vector DBs at every scale |
| 4 | Local Docker image: `pgvector/pgvector:0.8.6-pg18-trixie` | Checked current state (Aug 2026): Postgres 18 stable (supported to Nov 2030), Postgres 19 still in beta, pgvector 0.8.6 on the official actively-maintained image | Pinned full tag (not just `pg18-trixie`) so pgvector version can't silently drift. pgvector 0.8.x adds `halfvec` + DiskANN-family indexes — not needed now, relevant for Arm 5 storage tradeoffs later |
| 5 | Compose volume mount: `pgdata:/var/lib/postgresql` (not `.../data`) | First attempt mounted at `/var/lib/postgresql/data` (pre-pg18 convention) — container crash-looped on startup | Postgres 18+ images require the volume at `/var/lib/postgresql` so they can manage major-version-specific subdirectories for `pg_upgrade --link` support. Confirmed by container logs, verified working after fix (Postgres 18.6, pgvector 0.8.6 both live) |
| 6 | Parser: local, not Reducto (superseded by #9 for *which* local tool) | Reducto scores higher on complex tables (RD-TableBench) but costs $/page + API key | spec.md scopes parsing as "buy it, don't build it" at free/local tier — Reducto noted in writeup as build-vs-buy, not used |
| 7 | Corpus: real 10-Ks pulled live from EDGAR by (cik, report_year), not T²-RAGBench's shipped page-PDFs | Dataset ships single annotated pages (ConvFinQA only, 1,806 of them) — not full docs | Full filings make retrieval realistic (right page among hundreds, not the few the dataset pre-filtered to); avoids inflated recall@k. `src/rag_sec/edgar.py` |
| 8 | Day 2 dry run at 100 filings, not full corpus yet | `scripts/day2_ingest.py`: 100/100 parsed, 0 failures (re-run with sec-parser per #9: median 1.3s, was 4s w/ Docling) | Validate pipeline before sizing full ingest to the real need (799 filings, TAT-DQA unresolved) rather than an arbitrary 500/1000 |
| 9 | Parser: `sec-parser` (alphanome-ai), not Docling | Eyeballing found Docling shatters prose into tiny paragraphs (per-phrase `<font>` tags), leaks page numbers/ToC headers into text, mangles tables. `sec-parser` fixes the first two (verified on AAL/JPM/ETR); split-negative-number table cells (e.g. `(619`/`)`) are a source-HTML defect neither tool fixes | Ships only `Edgar10QParser`, no 10-K support — workaround strips its 10-Q section step via undocumented internals (`Elijas/sec-parser-exploration` notebook). Pinned exact (`==0.58.1`) since internals may break on upgrade; **fallback: Docling + normalization pass** (merge `<font>` runs, strip page/ToC noise). Relaxed `pandas` pin (`>=3.0.5`→`>=2.2.2,<3.0.0`, was arbitrary, unused by us) to satisfy it. New module `src/rag_sec/parsing.py`. Known gap: `find_item_boundaries` returns nothing for filers using narrative headings instead of "Item N" (e.g. JPM) — accepted, not blocking chunking v1 |
| 10 | Chunking v1: structure-aware packer, 200/900/1500-token min/target/max | Bounds set from T2-RAGBench's own evidence spans (median 630 words, p90 990 words), not a generic RAG default. Token-counted via BGE-M3's tokenizer (spec.md's primary embedding candidate), not chars — chars/token ratio measured at 4.1-4.5 for prose vs. 2.6-2.9 for tables, so a char budget would silently over/under-pack depending on content mix | Tables never split mid-row (row-group split w/ repeated header if a table alone exceeds max). Bug found in testing: filers lacking body-level "Item N" headings (decision #9's gap) produce single unstructured text blocks up to 18k tokens — over BGE-M3's 8192 hard limit, i.e. actually unembeddable, not just oversized. Fixed with `_split_text()`: sentence-boundary packing + raw-token-window fallback, mirroring the table splitter. Second bug (100-filing run): sec-parser sometimes misclassifies a long bold paragraph (exhibit-index entries, cross-refs, signature blocks) as a `TitleElement`. Checked every title >100 tokens across all 100 filings (16 total) — none are genuine headings — so reclassified anything over `MAX_TITLE_TOKENS=100` as body text. Empirical for this sample, not a proven law; failure mode is soft (a real long heading would just lose grouping, not corrupt data). Full 100-filing run: 11,391 chunks, median 885 tokens, max 1580, 0 over ceiling. `src/rag_sec/chunking.py` |
