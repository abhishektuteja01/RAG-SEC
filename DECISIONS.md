## Infra

| # | decision | why |
|---|---|---|
| INFRA-1 | Store: Postgres + pgvector, not a dedicated vector DB (Pinecone/Weaviate/Qdrant) | Dedicated vector DBs win at hundreds-of-millions+ scale (sharding, ANN specialization). Our corpus is ~100k chunks — HNSW on one instance handles that. Also need hybrid search (dense + BM25 + relational metadata) in one SQL query, not 2-3 systems plus consistency glue |
| INFRA-2 | Docker image pinned to `pgvector/pgvector:0.8.6-pg18-trixie` | Checked current state (Aug 2026): Postgres 18 stable (supported to Nov 2030), 19 still beta, 0.8.6 is pgvector's actively-maintained release. Pinned the full tag (not just `pg18-trixie`) so pgvector can't silently drift |
| INFRA-3 | Compose volume mount: `pgdata:/var/lib/postgresql` (not `.../data`) | First attempt used the pre-pg18 path and crash-looped on startup. Postgres 18+ needs the volume one level up so it can manage major-version subdirectories for `pg_upgrade --link` |
| INFRA-4 | BM25 extension: `pg_search` (ParadeDB), not `tsvector`/`ts_rank`, `VectorChord-bm25`, or `pg_textsearch` | `ts_rank` isn't real BM25 (no document-length normalization or term saturation — degrades on long filings). `VectorChord-bm25` would mean re-platforming off our pinned image (`INFRA-2`); `pg_textsearch` ships no package yet. `pg_search` has a prebuilt `.deb` for our exact base image, depends on pgvector rather than competing with it, AGPL (free self-hosted). Index: `USING bm25 (id, text)`; query: `id @@@ paradedb.match(...)` (literal-text match, default OR-mode — matches real BM25 semantics of IDF-weighted overlap, not require-all-terms) |

## Dataset & eval harness

| # | decision | why |
|---|---|---|
| DATA-1 | Primary eval set: T²-RAGBench (`G4KMU/t2-ragbench`), not FinanceBench | FinanceBench: only 150 of 10,231 triples are public — too small to gate on (~4pt stderr at n=150). T²-RAGBench: 23,088 rows / 7,318 docs, fully open. FinanceBench kept as a secondary sanity check only |
| DATA-2 | ConvFinQA split 80/10/10 by document (`context_id`, seed 42), not by row | Ships with no split. Grouping by document (not row) stops the ~1.9 questions/doc from leaking one document across splits. Actual: 78.3/11.5/10.2 by row, zero cross-split docs |
| DATA-3 | TAT-DQA deferred from the eval set | Ships no CIK, only slugified company names — exact-match resolved only 79/173 companies (some are foreign 20-F/40-F filers, permanently out of scope, not a resolution failure). FinQA+ConvFinQA alone give full CIK-resolved coverage without it |
| DATA-4 | Corpus: real 10-Ks pulled live from EDGAR by `(cik, report_year)`, retrieval scored against full filings — not T²-RAGBench's shipped single-page contexts | The dataset ships one annotated page per question; scoring against that inflates recall@k (right page among a handful, not among hundreds). Full filings are the realistic task, but the tradeoff is our recall/nDCG **aren't directly comparable to the paper's own leaderboard** — the paper's own baseline scores <80% even on its easier per-question contexts. State this plainly in the writeup |
| DATA-5 | `edgar.py`: match a 10-K by `reportDate` (period of report) year, not a `filingDate` window | The old filingDate-window logic broke on non-calendar-fiscal-year filers (Apple, Nike, Sysco, ...) — two consecutive fiscal years' 10-Ks could both land in the window, and EDGAR lists filings most-recent-first, so the wrong fiscal year got picked. Audit found 26/100 filings affected (128/1,100 eval questions); re-fetched and re-chunked all 26 |
| DATA-6 | Corpus grown in stages: 100 → 300 → 400 → 603 → 799 filings, ending at full FinQA+ConvFinQA coverage (799 = exact count of unique `(cik, report_year)` pairs across both subsets, confirmed by direct count) | Each growth step invalidates prior Arm numbers by construction (more filings = more distractor chunks) — Arm 1-3 must be re-run unchanged after every corpus change. One growth (300→400) was an accidental second ingest run with a different seed that went unnoticed in CLAUDE.md/memory; caught only by checking the DB row count against the filesystem instead of trusting the doc. **Rule adopted: verify corpus size against the DB/filesystem, never against CLAUDE.md or memory, before trusting a number** |
| DATA-7 | Gold-relevance labeling v1: 5-gram shingle containment ≥0.3 vs whole-page `context`, not exact numeric match | Numeric match rejected (scaled `original_answer` often has no literal match). Threshold tuned 0.5→0.3 dropped zero-hit rate 28.5%→3%. **Superseded by `GOLD-1`** — whole-page matching itself had unfixed bugs |
| DATA-8 | Added numeric-literal overlap as a second signal, OR'd with shingling, threshold 0.5 | Fixed a confirmed undercounting bug (number repeated in two formats, e.g. `-17.1 ( 17.1 )`) on 2 cases; ~10 filings flagged as still affected, not fully rescued. **Superseded by `GOLD-1`** |
| DATA-9 | IDF-weighted overlap + minimum-evidence floor (`MIN_NUMERIC_EVIDENCE=3`) | Fixed two false-positive-flooding bugs (trivial 1-2-number denominator; decimal-only regex missed whole-integer tables). Zero-hit questions 2→0 on 300 dev rows. **Superseded by `GOLD-1`** — table/chunk-boundary splits remained uncaught, which is what motivated the rebuild |

## Chunking

| # | decision | why |
|---|---|---|
| CHUNK-1 | Parser: `sec-parser` (alphanome-ai, pinned `==0.58.1`), not Docling | Docling shatters prose into per-phrase fragments, leaks page-number/ToC noise into text, and mangles tables (eyeballed on AAL/JPM/ETR). `sec-parser` fixes the first two and parses ~3x faster (1.3s vs 4s/filing), but ships only 10-Q support — worked around via undocumented internals to reuse it for 10-Ks, so pinned exactly since those internals may break on upgrade. Known gap: `find_item_boundaries` returns nothing for filers using narrative headings instead of "Item N" (e.g. JPM) — accepted, not blocking. Fallback path if this ever breaks: Docling + a normalization pass (merge `<font>` runs, strip page/ToC noise) |
| CHUNK-2 | Chunk bounds 200/900/1500 tokens (min/target/max), token-counted via BGE-M3's tokenizer, not characters | Bounds come from T²-RAGBench's own evidence-span lengths (median 630 words, p90 990), not a generic RAG default. Token-counting matters because chars/token ratio measured at 4.1-4.5 for prose vs. 2.6-2.9 for tables — a character budget would silently over/under-pack depending on content mix. Tables are never split mid-row; an oversized table splits by row-group with the header row repeated in each group |
| CHUNK-3 | Two chunking-bug fixes found in the 100-filing dry run | (a) Filers lacking body-level "Item N" headings (`CHUNK-1`'s gap) produced single unstructured blocks up to 18k tokens — over BGE-M3's 8192 hard limit, i.e. actually unembeddable. Fixed with sentence-boundary packing + a raw-token-window fallback splitter. (b) `sec-parser` sometimes misclassifies a long bold paragraph (exhibit-index entries, signature blocks) as a heading — every title >100 tokens across all 100 filings was checked by hand (16 total, none genuine) and reclassified as body text. Empirical for this sample, not a proven rule; failure mode is soft (a real long heading would just lose grouping) |

## Arm 1 — dense retrieval

| # | decision | why |
|---|---|---|
| ARM1-1 | Embedding: BGE-M3 dense vector via `sentence-transformers`, not `FlagEmbedding` | `FlagEmbedding`'s `BGEM3FlagModel` also computes sparse + multi-vector (ColBERT-style) representations in one pass — not needed for a dense-only baseline. Both libraries wrap identical model weights, so the dense vector doesn't change if a later arm adds `FlagEmbedding` for sparse. 1024-dim, cosine distance, pgvector HNSW index |
| ARM1-2 | Retrieval: pure semantic search over the whole corpus, no `cik`+year metadata pre-filter | A pre-filter would raise recall by construction now that `DATA-5` makes that lookup reliable — but Arm 1 is the fixed baseline every later arm is compared against, and pre-filtering would change what's being measured, not just how well. Logged as a candidate variant for later, not blended into the baseline |
| ARM1-3 (open) | BGE-M3 uses single-`[CLS]` pooling (`sentence-transformers` default), not BAAI's MCLS long-document pooling (only exposed via `FlagEmbedding`, skipped per `ARM1-1`) | A chunk-length slice of Arm 1's results shows a real gradient — recall@10 0.50 (short chunks) vs 0.41 (medium) vs 0.26 (long) — consistent with a long-document pooling weakness. Correlational, not proof: long chunks overrepresent filers hit by `CHUNK-3`'s bug, and the labeling threshold wasn't separately validated per length bucket. Logged as a candidate to re-check with `FlagEmbedding` + MCLS before adopting |

## Arm 3 — reranker

| # | decision | why |
|---|---|---|
| ARM3-1 | Reranker: `bge-reranker-v2-m3` (local cross-encoder) over Arm 2's fused top-50, not Qwen3-Reranker-0.6B | Checked current state (Aug 2026): Qwen3-Reranker edges out on BEIR (~59 vs ~54) but is a causal yes/no-logit architecture — autoregressive decode per candidate. `bge-reranker-v2-m3` is a plain bidirectional cross-encoder: one forward pass, one score, and spec.md asks us to measure nDCG gain *against* latency cost, so the cleaner latency story won out over the leaderboard number. Cohere Rerank (hosted) deliberately deferred to conserve free-tier call budget |
| ARM3-2 | Reranking run offloaded to Northeastern's HPC (SLURM, V100) via a split-job pattern, not laptop CPU or a live SSH tunnel | Laptop CPU run swap-thrashed under normal load (~110s/query plateau, ~25h projected — not viable). A live tunnel from the GPU node to the laptop's Postgres was rejected: a dropped connection kills the whole run, same failure mode as the CPU run but now burning a SLURM allocation too. Split-job instead: laptop does the cheap retrieval + dumps a payload file; a self-contained, checkpointed GPU script reranks with no DB/network dependency; laptop scores the results after. File transfers must go through `xfer.discovery.neu.edu` — the interactive login node throttles/kills large transfers |
| ARM3-3 | Added cross-question batching to the HPC rerank script (20 questions' pairs per `predict()` call) | Only ~12% speedup (5.07s→4.45s) — GPU compute time, not Python call overhead, was the dominant cost, so batching couldn't buy the order-of-magnitude win hoped for. Adopted anyway since it's free |
| ARM3-4 (open) | Reranker introduces a same-company-wrong-fiscal-year failure mode not seen in Arms 1/2 | E.g. a JPM_2008 question's top hits are JPM_2009/2010 chunks; consecutive 10-Ks from the same filer share near-identical boilerplate, and a cross-encoder trained on general relevance has no inherent signal that the year token is decisive. Candidate fix: metadata-aware reranking or a `cik`+year filter — not yet built |

## Arm 4 — table indexing strategies (A/B/C)

| # | decision | why |
|---|---|---|
| ARM4-1 | Strategy B: one standalone chunk per table row (header repeated in each), bypassing the normal token packer | Tests whether row-level granularity beats retrieving the whole table. Standalone so a row never gets diluted by unrelated narrative sharing its chunk — the point of testing row granularity is lost otherwise |
| ARM4-2 | Strategy C: raw table chunk (identical serialization to Strategy A) + a separate standalone LLM-summary chunk, indexed *alongside* the raw table, not replacing it | Tests whether a paraphrased description helps recall beyond raw pipe-delimited text. Kept alongside rather than swapped in, so a bad summary can't regress below the Strategy-A baseline for that table |
| ARM4-3 | B/C scoped to only the 498 tables actually cited as gold evidence by dev questions (of 38,959 tables across 324 dev-relevant filings), identified via the same IDF-weighted shingle+numeric matching `eval.py` already uses (`DATA-7`–`DATA-9`), applied table-vs-table instead of question-vs-chunk | Embedding/summarizing all 38,959 tables costs compute and (for C) LLM calls for tables no dev question ever touches. Every non-target table stays Strategy A |
| ARM4-4 | Chunk-boundary drift bug (found in verification) + fix: `chunk_blocks_with_variant` builds plain Strategy-A chunks first, then splices a target table's atoms out of whichever chunk(s) they landed in, instead of re-running the packer with different atoms | Root cause: B/C's standalone atoms (row chunks, summary) forced the token-packer to close the current chunk early regardless of token budget, which shifted every downstream chunk boundary in that section — corrupting ~50% of filings with stray, unrelated re-chunked text that had nothing to do with any table. Splicing onto already-decided boundaries means only the one chunk containing the target table changes; verified byte-identical elsewhere on a full rebuild (281 filings) |
| ARM4-5 | Gold-relevance labeling: added a direct table-provenance match for Strategy C summary chunks (chunk text matches a cached summary for a table that's gold for this question), OR'd with the existing shingle/numeric checks | Existing labeling scores relevance by wording overlap against the dataset's gold text. An LLM-paraphrased summary routinely fails that check even when correct — measured ~19% of gold-table cases would be mislabeled "not relevant" purely from wording, understating Strategy C's real recall. Purely additive (only adds relevant labels), verified against a real case (sh_score 0.003, num_score 0.33, both below threshold, now correctly marked relevant) |
| ARM4-6 | Table summarizer: Claude Haiku 4.5, not Groq `openai/gpt-oss-120b` | A 50-table spot-check of the Groq summaries found a 22% comprehension error rate (wrong trend direction, column/label misattribution, unit confusion) plus a reasoning-token budget bug. Switched to Haiku with a checklist prompt targeting those failure classes + a forced show-your-work step. Re-audited 40 summaries post-switch: 7.5% error rate, all the same residual shape — picking the wrong endpoint for a multi-quarter/multi-year range or trend instead of the true min/max/direction, not fabrication or unit errors |
| ARM4-7 | Normalize dash/em-dash "zero" placeholder cells (e.g. `—`) before sending a table to the summarizer, not via prompt instruction alone | A prompt-only instruction to treat dashes as zero didn't reliably hold — the model still sometimes misread them as missing data. Fixed at the data layer instead of relying on the LLM to apply the rule consistently |
| ARM4-8 | Delta-only embedding: `day6_build_table_variants.py` embeds/inserts only chunks whose text doesn't already exist as a Strategy-A row for that filing, not the whole filing per variant | Re-embedding a filing's full ~100-250 chunks for every variant would cost ~100x more than needed — B/C only ever add a handful of small new chunks (rows, summary) per filing. Runs locally on CPU in minutes; no HPC needed for this step (HPC is reserved for the full-corpus embed and Arm 3's reranking, both far larger jobs) |
| ARM4-9 (open) | 224/1235 dev questions have no matched gold table at all, excluded from the A/B/C comparison | Same shingle+numeric matching as `ARM4-3` found no table clearing the relevance threshold for these — likely a mix of real corpus gaps (per `DATA-5`/`DATA-8`) and questions whose evidence isn't in table form. Not chased further; logged as a known gap in eval coverage |
| ARM4-10 | Result: Strategy A beats B and C on every metric (baseline table above) — kept A, B/C not adopted | Splitting a table into rows (B) or adding a paraphrased summary (C) both regress recall@10 by ~0.15-0.19 vs. the whole table. B and C are close on recall/nDCG, but C's MRR (0.390) clears B's (0.291) despite lower recall — C offers only 2 candidate representations per table (raw + summary) vs. B's one-per-row, so B gets more chances to register a hit but each is a narrower target, while C's fewer candidates rank higher when they do hit |

## Arm 5 — late interaction / multi-vector (dropped)

| # | decision | why |
|---|---|---|
| ARM5-1 | Arm 5 (BGE-M3 late-interaction/multi-vector, spec.md Day 7) dropped entirely, not built even as a pilot | Measured against our real corpus before building anything: 99,654 chunks, avg 927 tokens/chunk (median 887). BGE-M3's multi-vector output is confirmed 1024-dim *per token*, no dimension reduction (unlike ColBERT's 128-dim projection) — checked current docs/HF card, Aug 2026. Storage: Arm 1 dense = 99,654 × 1024 × 4B ≈ 389MB; Arm 5 multi-vector = 99,654 × 927 × 1024 × 4B ≈ 378GB, a ~972x blowup, before even indexing it. Worse than storage: MaxSim retrieval needs an ANN index over ~92M token-vectors, not 99,654 chunk-vectors — pgvector/HNSW has no native MaxSim support, so this would mean building a custom PLAID-style index with no guaranteed quality win, since our chunks are already well inside BGE-M3's context window (median 887 tokens) — late interaction's main advantage (rescuing signal in very long documents) isn't clearly our bottleneck. Per spec.md's own framing, reporting this honestly is a stronger result than building it to prove the obvious |

## Gold-relevance labeling rebuild (`gold_inds`, not whole-page overlap)

| # | decision | why |
|---|---|---|
| GOLD-1 | Replaced the IDF-weighted shingle/numeric-overlap labeler (`DATA-7`-`DATA-9`, scored against T2-RAGBench's whole-page `context`) with a 3-layer design: (1) exact numeric match against a specific table row, (2) word-position alignment against a specific sentence, (3) word-position alignment against the whole page as fallback — using `gold_inds` from the *original* FinQA/ConvFinQA datasets (upstream of T2-RAGBench, which flattens `pre_text`/`post_text`/`table` back to strings and drops `gold_inds` entirely). Fetched + ID-matched by (ticker, year, page_number) + numeric-answer tiebreak: 95.1% of the full 11,739-row corpus resolved (FinQA ~98%, ConvFinQA ~87-90% — lower because ConvFinQA puts multiple full conversations on the same page, so the join key is ambiguous more often); the remaining 4.9% use Layer 3 only. `data/day7_gold_inds_matched_full.json` (raw match) -> `scripts/eval/day7_resolve_gold_evidence.py` -> `data/day7_gold_evidence_resolved.json` (literal row cells / sentence text, so `eval.py` never touches the raw multi-hundred-MB dataset files at scoring time) | Auditing `AUDIT-1`'s "0 labeling misses" claim by hand (not just re-running the same formula) found the old approach's real bugs: a Table-of-Contents entry or repeated financial-statement header can share 10-20+ verbatim words with the true answer section purely from page boilerplate and score as relevant (`finqa_train_2408`/DISH: TOC entry for "Item 5" matched 43 chunks before the real Item 5 section); a paragraph split across our chunk boundary systematically under-scores the smaller half, since containment is computed against the *whole* gold page (`finqa_dev_11`/PKG: the chunk with the literal answer table scored 0.10 shingle / 0.0 numeric, both below threshold). Matching against one specific row or sentence instead of a whole page removes the ambiguity these came from, rather than patching each pattern individually — the explicit goal, not a side effect (spec.md's own framing: a whole page is inherently loose ground truth once two independent parsers are involved, `DATA-4`) |
| GOLD-2 | Tokenizer fixes needed before Layer 1 numeric matching was usable: (a) collapse comma thousands-separators before splitting words (`6,951` -> one token `6951`, not `6`+`951`); (b) keep decimals as one token (`384.3`, not `384`+`3`) | Our chunk serialization renders `$6,951`; the source renders `6951` — without (a), the exact same figure produces a different token count on each side and never matches. Found while confirming (b) doesn't already exist: `[a-z0-9]+` splits on the decimal point too, both fragmenting a real figure into two weaker signals *and* creating a generic, noisy `3`-style token as a side effect |
| GOLD-3 | Layer 1's "distinctive number" filter needed three exclusions, not one, found by running the rebuilt labeler over the full dev set and inspecting every case with an unexpectedly large relevant-chunk count before locking any values: numbers under 3 digits, years (1900-2099), and — the one IDF weighting used to catch in the old design — any number recurring in more than `ROW_NUMBER_MAX_DOC_FREQ=5` of the *same filing's* own chunks | Each was a real, confirmed false-positive case, not a hypothetical: a bare `4` (from a `(4)` footnote marker) matched an unrelated debt-rating paragraph (`finqa_dev_17`/MSI); a row's only other "distinctive" number was `2003`, the filing's own fiscal year, which matched 130/401 of that filing's chunks (`finqa_dev_321`/AES); a `100%` column-total matched 21 chunks across unrelated percentage tables in the same filing (`finqa_dev_126`). Committing to "no more IDF weighting" (`GOLD-1`'s stated goal) still left this one narrow case where *some* document-frequency check was unavoidable — full IDF re-weighting wasn't needed, just a hard cutoff, since Layer 1 only ever compares within one filing's own chunks, not across the corpus |
| GOLD-4 | Calibrated `MIN_BLOCK_PAGE=10`, `MIN_BLOCK_SENTENCE=6`, `MAX_CLUSTER_GAP=3`, `CLUSTER_SHARE_THRESHOLD=0.15`, `ROW_NUMBER_MATCH_THRESHOLD=0.6` against the full 1235-row dev set (not a small held-out sample — every row was checked automatically via the zero-hit-rate and largest-relevant-set metrics, with manual inspection of every outlier), not picked upfront | Result: 0% zero-hit rate (every dev question has >=1 relevant chunk under the new labeler — down from checking against `AUDIT-1`'s definition), median relevant-chunks-per-question 1, max 6 (down from an uncalibrated first pass's max of 130, per `GOLD-3`). All 7 named regression cases (5 recovered failures, 2 rejected false positives) verified individually after locking these values, not just in aggregate |
| GOLD-5 | Rescored every existing arm's already-computed retrieval output against the new labels — Arm 3/4 offline from saved reranked orderings (`data/day6_arm4_*_rerank_scores.jsonl`, `data/rerank_scores.jsonl`, no HPC/reranking re-run), Arm 1/2 via a local retrieval re-run (dense+BM25/RRF only, no reranking, no HPC — the ranking logic itself is unchanged, only relevance labels differ) | Every arm's recall improved substantially (see baseline table) — e.g. Arm 3/4-A recall@10 0.501 -> 0.609 — confirming the old labeler was genuinely under-counting relevant chunks, not that today's retrieval was secretly better than measured. Arm 4's qualitative finding (`ARM4-10`: A beats B and C) is unchanged under the corrected labels — B and C's recall@10 (0.350/0.352) are within noise of their old numbers (0.356/0.309), so that comparison wasn't distorted by the old labeler's bugs, only the absolute ceiling was |
| GOLD-6 (open) | ConvFinQA's `gold_inds` match is exact for only 15% of matched rows (`Double_*` dialogues, which record real per-turn evidence) — the other 85% (`Single_*` dialogues) borrow the *final* conversation turn's `gold_inds` as a proxy for our first-turn-only question, since ConvFinQA's raw annotation only records evidence on the last turn. Not chased further: the proxy is a superset (final-turn evidence is very likely a superset of first-turn evidence for short chains) and Layer 3 fallback still applies if a chunk match ends up empty. Also open: the 4.9% of the corpus (mostly ambiguous ConvFinQA joins, `DATA-2`) that never resolved a `gold_inds` match at all use Layer 3 (whole-page) only — same approach as before this rebuild for that slice |
| GOLD-7 | The ticker/year/page/numeric-tiebreak join that produced `data/day7_gold_inds_matched_full.json` was run ad hoc against manually-fetched raw FinQA/ConvFinQA files and never saved as a script — only the downstream resolver (`day7_resolve_gold_evidence.py`) is committed | Shortcut, logged per rule 5: `data/day7_gold_inds_matched_full.json` is committed as data (not regeneratable from anything in-repo) rather than reproducible from a script. Re-deriving it would mean rewriting the join logic from scratch |
