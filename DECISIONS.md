## Standing rules — how to quote this log

One more rule, which never needed a row of its own: a run that would change a published
result writes a sidecar (`data/*_companyfilter.json`) instead of overwriting the file, so
both sets stay reproducible from the same script — the same reasoning as the
`.bak_old_labeler` files.

| # | decision | why |
|---|---|---|
| DATA-6 | Corpus grown in stages to 799 filings — the exact count of unique `(cik, report_year)` pairs across FinQA+ConvFinQA, confirmed by direct count | Each growth step invalidates prior Arm numbers by construction (more filings = more distractor chunks), so Arms 1-3 must be re-run unchanged after every corpus change. One growth was an accidental second ingest run with a different seed that went unnoticed in the notes, caught only by checking the DB row count against the filesystem. **Rule adopted: verify corpus size against the DB or the filesystem, never against a doc or a memory, before trusting a number** |
| INFRA-19 | The 9.4x loop-cost multiplier has no establishable provenance. This row records the **absence**, not the number: do not quote 9.4x — re-derive it or drop it | Searched 2026-09-03: nothing in `data/` or `scripts/` produces it, and `git log -S` across all branches shows it only ever in one line of a personal working note. The nearest candidates are coincidences, and `COST-24` marked those figures suspect. No row asserting the number was ever added, deliberately: a row here is a provenance claim, and inventing one is worse than the number having no home |
| INFRA-21 | Diagnose latency with the metric for the machine you are on, and **never publish a latency without the machine state beside it** | Three mechanisms so far and none was guessed. Battery and thermals were wrong both times: on the laptop it was MPS's caching allocator not returning freed blocks (`AGENT-24`), where `ps` RSS read 0.1 GB against 7 GB of swap growth because it cannot see MPS buffers; on AWS it was burstable CPU credits (`DEPLOY-17`). | INFRA-22 | The project's recurring failure mode, at seven instances: **code or prose reusing a number, shape, or artifact without checking which job produced it.** Check provenance before quoting a number, including your own | Instances: `compress.chunk_atoms` indexed a replayed packer output with a Postgres-derived `chunk_index` and returned the wrong atoms silently (guarded 2026-09-07); `RETR-24` (B/C chunks scored as A); `RETR-30`'s mis-anchored GPU-hour estimate and its near-miss filename clobber; `AGENT-16` (static rankings read in first-stage order); `GOLD-7`; `INFRA-17`. ## Store and corpus

| # | decision | why |
|---|---|---|
| INFRA-1 | Store: Postgres + pgvector, not a dedicated vector DB (Pinecone/Weaviate/Qdrant) | Dedicated vector DBs win at hundreds-of-millions+ scale (sharding, ANN specialization). Our corpus is ~100k chunks — HNSW on one instance handles that. We also need hybrid search (dense + BM25 + relational metadata) in one SQL query, not 2-3 systems plus consistency glue |
| INFRA-2 | Docker image pinned to `pgvector/pgvector:0.8.6-pg18-trixie`, with the volume mounted at `pgdata:/var/lib/postgresql` | Checked current state (Aug 2026): Postgres 18 stable (supported to Nov 2030), 19 still beta, 0.8.6 is pgvector's actively-maintained release. Pinned the **full tag** (not just `pg18-trixie`) so pgvector can't silently drift. The volume path is a consequence of the pin: the first attempt used the pre-pg18 `.../data` path and crash-looped on startup, because Postgres 18+ needs the volume one level up so it can manage major-version subdirectories for `pg_upgrade --link` |
| INFRA-4 | BM25 extension: `pg_search` (ParadeDB), not `tsvector`/`ts_rank`, `VectorChord-bm25`, or `pg_textsearch` | `ts_rank` isn't real BM25 (no document-length normalization or term saturation — degrades on long filings). `VectorChord-bm25` would mean re-platforming off our pinned image (`INFRA-2`); `pg_textsearch` ships no package yet. `pg_search` has a prebuilt `.deb` for our exact base image and depends on pgvector rather than competing with it. The query is `id @@@ paradedb.match(...)` in default OR-mode, which matches real BM25 semantics of IDF-weighted overlap rather than require-all-terms |
| DATA-1 | Primary eval set: T²-RAGBench (`G4KMU/t2-ragbench`), not FinanceBench | FinanceBench: only 150 of 10,231 triples are public — too small to gate on (~4pt stderr at n=150). T²-RAGBench: 23,088 rows / 7,318 docs, fully open. FinanceBench kept as a secondary sanity check only |
| DATA-2 | ConvFinQA split 80/10/10 by document (`context_id`, seed 42), not by row | Ships with no split. Grouping by document rather than row stops the ~1.9 questions/doc from leaking one document across splits. Actual: 78.3/11.5/10.2 by row, zero cross-split docs |
| DATA-3 | TAT-DQA deferred from the eval set | It ships no CIK, only slugified company names — exact-match resolved only 79/173 companies, and some are foreign 20-F/40-F filers that are permanently out of scope rather than a resolution failure. FinQA+ConvFinQA alone give full CIK-resolved coverage |
| DATA-4 | Corpus: real 10-Ks pulled live from EDGAR by `(cik, report_year)`, retrieval scored against **full filings** — not T²-RAGBench's shipped single-page contexts | The dataset ships one annotated page per question; scoring against that inflates recall@k (right page among a handful, not among hundreds). Full filings are the realistic task. The tradeoff is that our recall/nDCG aren't directly comparable to the paper's own leaderboard — the paper's baseline scores <80% even on its easier per-question contexts. State this plainly in the writeup |
| DATA-5 | `edgar.py`: match a 10-K by `reportDate` (period of report) year, not a `filingDate` window | The old filingDate-window logic broke on non-calendar-fiscal-year filers (Apple, Nike, Sysco, ...) — two consecutive fiscal years' 10-Ks could both land in the window, and EDGAR lists filings most-recent-first, so the wrong fiscal year got picked. Audit found **26/100 filings affected** (128/1,100 eval questions); re-fetched and re-chunked all 26 |
| INFRA-8 | Three staged ingest scripts folded into one `scripts/pipeline/01_corpus.py` that takes the whole 799-filing pool — no sampling, no seed | The sampling was an artifact of growing the corpus in stages (`DATA-6`), not a design: once 799 *is* the pool, the seed and sample size are pure downside — they are what let `DATA-6`'s accidental duplicate run happen. The documented rebuild was also broken: the README's two-step recipe tracked progress via a directory the first step never writes, so a newcomer got ~300 filings while every published number is against 799. **Verified non-destructively before deleting anything** — 25 filings re-chunked in memory give identical chunk count, text, headings and token counts, because the natural check would have overwritten the thing being checked. `--reparse` closes a real gap: the old script reused `data/parsed/` whenever it existed, so a `parsing.py` change was silently ignored |
| INFRA-12 | The `RETR-7` re-index is an incremental re-embed of **47.5%** of the corpus, not a full one — measured, not estimated | Because boundaries are preserved, `(filing_stem, chunk_index, variant)` still identifies the same body text, so only chunks whose *text* changed need a new vector. This is the payoff for refusing the flush variant: under flush-on-title every chunk index shifts, so 100% needs re-embedding *and* every gold label has to be re-derived. No GPU-hour figure is quoted here on purpose — the only durable anchor on disk is an earlier embed payload, so scale from that. Recorded because it was a real mistake: a first attempt ran the embedding locally on MPS and was aborted; those rows are still in the payload, because the changed set is computed by diffing chunks against the pre-fix backup, never against DB state |
| INFRA-13 | BGE-M3 embedding throughput on the HPC V100, measured: from `sacct`, **47,312 chunks in ~72 minutes ≈ 11 chunks/s** at `BATCH_SIZE=64`, so a full 99,654-chunk pass is ~2.5 GPU-h | Recorded because its absence had been a standing provenance hole, alongside the unsourced 9.4x (`INFRA-19`) and `RETR-30`'s mis-anchored GPU-hours. Two caveats kept deliberately: the allocation includes model load and idle time, so 72 min is the embedding and 76 the booking; and this is a V100 at ~900-token chunks, so it does not transfer to the reranker, a different model on different input. Counter-anchor worth keeping beside it: the same job on this laptop's MPS measured ~8x slower, which is why embedding belongs on HPC |

## Chunking, and the heading fix

| # | decision | why |
|---|---|---|
| CHUNK-1 | Parser: `sec-parser` (alphanome-ai, pinned `==0.58.1`), not Docling | Docling shatters prose into per-phrase fragments, leaks page-number/ToC noise into text, and mangles tables (eyeballed on AAL/JPM/ETR). `sec-parser` fixes the first two and parses ~3x faster, but ships only 10-Q support — worked around via undocumented internals to reuse it for 10-Ks, hence the exact pin. Known gap: `find_item_boundaries` returns nothing for filers using narrative headings instead of "Item N" (e.g. JPM) — accepted, not blocking. Fallback if this breaks: Docling plus a normalization pass |
| CHUNK-2 | Chunk bounds 200/900/1500 tokens (min/target/max), token-counted via BGE-M3's tokenizer, not characters | Bounds come from T²-RAGBench's own evidence-span lengths (median 630 words, p90 990), not a generic RAG default. Token-counting matters because the chars/token ratio measured 4.1-4.5 for prose against 2.6-2.9 for tables — a character budget would silently over- or under-pack depending on content mix. Tables are never split mid-row; an oversized table splits by row-group with the header row repeated in each group |
| CHUNK-3 | Two chunking-bug fixes found in the 100-filing dry run | (a) Filers lacking body-level "Item N" headings (`CHUNK-1`'s gap) produced single unstructured blocks up to 18k tokens — over BGE-M3's 8192 hard limit, i.e. **actually unembeddable**; fixed with sentence-boundary packing plus a raw-token-window fallback. (b) `sec-parser` sometimes misclassifies a long bold paragraph (exhibit-index entries, signature blocks) as a heading; every title >100 tokens across the sample was checked by hand and none was genuine. Empirical for this sample, not a proven rule; the failure mode is soft — a real long heading would just lose grouping |
| `RETR-7` (diagnosis + fix, merged; built, dark) | Heading bug in `chunking._pack_atoms`: chunks carried a heading set *after* some of their own body text. **Fixed without moving a single chunk boundary** — `_pack_atoms` now records the heading each atom sits under when the atom is buffered, and labels each chunk with every section it spans. Re-measured over all 799 filings: 45.9% of atoms sat under a heading they did not come from, 54.7% of those an unrelated topic | The bug: a title atom only flushed the buffer when the token count was already at target; below that it just overwrote `current_heading`, so a short section's text was emitted under the *next* section's heading — a balance sheet headed `# CREDIT RISK`, a factory-count table headed `# Performance Graph`. The heading is a signal we deliberately inject to help retrieval, and it was misleading on nearly half the corpus: a correctness bug regardless of recall impact. Boundary preservation is the point of the fix and it is enforced, not hoped for — `eval.py` recomputes labels from chunk *text* every run, so moving boundaries would renumber every gold label and make the new numbers incomparable to every published one. Four alternatives were measured and rejected: labelling by first body atom leaves a third of the misattribution (35.2% of chunks genuinely span two sections), blanking mixed headings is worse, flushing at every title moves 45% of boundaries, fold-back drops 28% of chunks under the minimum. A check asserts gold labels unchanged on 300/300 dev questions. No recall claim is attached |
| `RETR-8` (diagnosis + fix, merged; built, dark) | Page furniture and filer-agent junk no longer become a heading, **by structural class rather than by blocklist**, applied at the blocks→atoms boundary so it needs no re-parse. Furniture atoms keep `is_title`, so boundaries do not move; they simply never set the heading | What was in the heading slot: `# F-58`, `# PART II`, `# /s/ KPMG LLP`, `# 102013 PPG ANNUAL REPORT AND FORM 10-K`, and pre-2008 EDGAR typesetter metadata (`# ZEQ.=3,SEQ=66,EFW="2112402",CP="ABIOMED,INC."...`). In one case the running-header chunk beat the real answer because the question said "according to the 2013 PPG Annual Report and Form 10-K" — page furniture matching query furniture. The frequency rule is the one worth defending, because the obvious version is wrong: "a title repeating N times in one filing is a running header" deletes *real* financial-statement headings at N>=3 (`income taxes` repeats >=3x in 69 filings). At N>=10 all 49 distinct strings in the corpus are furniture. The page-label regex was tightened for the same reason — the loose form also swallows the exhibit index and accounting references, which are content. Ordering is not free: `RETR-8` cannot follow `RETR-7`, because the strip applies to the reranker only, so `RETR-7`'s extra headings would push more filing boilerplate into text scored by an unstripped query |
| INFRA-11 | Both fixes originally shipped **off** behind `RAG_SEC_MULTI_HEADING` / `RAG_SEC_STRIP_TITLE_FURNITURE`, flippable from the environment with no code edit. Off was byte-identical to the pre-fix packer: 99,654/99,654 chunks replay byte-for-byte | Not caution for its own sake — `rag_sec.compress` replays this packer from `data/parsed/` and requires it to reproduce the already-built `data/chunks/` exactly, so turning either flag on without a re-chunk would silently make compression select atoms from a different document than the one that was embedded and retrieved. The flags made the fix inert until the re-index cycle and made the A/B a one-variable change rather than a revert. Both now default ON (`RETR-39`) — see `INFRA-26` |
| INFRA-26 (open) | **Byte-identity has not been re-verified since the flags flipped on.** `INFRA-11`'s 99,654/99,654 replay was measured flags-*off* against the pre-re-index corpus; the identity that matters now is flags-*on* against the post-`RETR-39` corpus, and no row records checking it | Left open rather than assumed because the failure is silent: if the replayed packer and the stored corpus disagree, `compress` selects atoms from a different document than the one embedded and retrieved, and nothing errors. Run `scripts/checks/atom_replay.py` before trusting `compress` or `COST-5`. Cheap to close — no GPU, no database, no spend |
| RETR-39 | The re-index was executed end to end and every arm re-measured: **a corpus-wide correctness fix with no measurable effect on retrieval, exactly as forecast.** Boundaries, chunk count and gold labels unchanged, so all four Arm 3 cells are directly comparable to the published ones — only the corpus differs. Every cell moves inside stderr, and the superadditive interaction replicates on both splits | The prediction was made before building and it held: `RETR-33` measured `no_gold_chunk` = 0% twice, and the heading is a median 0.91% of a chunk's tokens. Do not retroactively reframe this as a recall play because a number moved — what it bought is that 45.9% of atoms no longer sit under a heading from another section. `unfiltered_stripped` moves recall@50 by exactly +0.000 while moving recall@10, which is a rerank-only change reordering the top without touching the pool, and is the internal check that the cells are wired correctly. Arm 1/2 are finally off the old labels, but corpus *and* labels changed at once, so no delta may be quoted for them |

## Gold labels

| # | decision | why |
|---|---|---|
| DATA-7 | Gold-relevance labeling v1 and its two patches, all **superseded by `GOLD-1`**: 5-gram shingle containment ≥0.3 against the whole-page `context`; then numeric-literal overlap OR'd in at threshold 0.5; then IDF-weighted overlap plus a minimum-evidence floor (`MIN_NUMERIC_EVIDENCE=3`) | Exact numeric match was rejected up front, since a scaled `original_answer` often has no literal match. Tuning the threshold 0.5→0.3 dropped the zero-hit rate 28.5%→3%. Numeric overlap fixed a confirmed undercounting bug (a number repeated in two formats, e.g. `-17.1 ( 17.1 )`) on 2 cases, with ~10 filings flagged as still affected and not fully rescued. IDF weighting plus the floor fixed two false-positive-flooding bugs — a trivial 1-2-number denominator, and a decimal-only regex that missed whole-integer tables — taking zero-hit questions 2→0 on 300 dev rows. **What none of it could fix is why it was replaced:** whole-page matching was itself unsound, and table/chunk-boundary splits stayed uncaught |
| GOLD-1 | Replaced the shingle/numeric-overlap labeler with three layers — exact numeric match against a specific table row, alignment against a specific sentence, whole-page alignment as fallback — using `gold_inds` from the *original* FinQA/ConvFinQA, which T2-RAGBench flattens and drops. **95.1% resolves** | The motivation was a hand audit of all 401 zero-recall dev questions (not a sample): 100% already had a labeler-confirmed relevant chunk, across every sub-pattern. That ruled out the labeler *failing to find* the right chunk — but it only checked internal consistency, so it could not see that the scoring formula itself was wrong, and its own conclusion is retracted. Auditing it by hand found the real bugs: a ToC entry or a repeated statement header can share 10-20+ verbatim words with the true answer section purely from page boilerplate and score as relevant (one matched 43 chunks), and a paragraph split across our chunk boundary systematically under-scores the smaller half, since containment is computed against the whole gold page. Matching one specific row or sentence removes the ambiguity rather than patching each pattern: **a whole page is inherently loose ground truth once two independent parsers are involved** |
| GOLD-3 | What Layer 1 needed before it worked: two tokenizer fixes, then a "distinctive number" filter with **three** exclusions, not one — numbers under 3 digits, years (1900-2099), and any number recurring in more than `ROW_NUMBER_MAX_DOC_FREQ=5` of the same filing's own chunks | The tokenizer fixes: collapse comma thousands-separators before splitting words (`6,951` → one token `6951`), because our chunk serialization renders `$6,951` while the source renders `6951`; and keep decimals as one token (`384.3`), because `[a-z0-9]+` splits on the decimal point, both fragmenting a real figure into two weaker signals and creating a generic noisy `3` token. ## Arms 1-3 — the retrieval ladder

| # | decision | why |
|---|---|---|
| ARM1-1 | Embedding: BGE-M3 dense vector via `sentence-transformers`, not `FlagEmbedding` | The other library computes three kinds of vector at once — dense, sparse and multi-vector — and a dense-only baseline needs one of them. Both libraries wrap the same model weights, so the dense vector is identical either way, and a later arm can add `FlagEmbedding` for sparse without changing Arm 1. 1024-dim, cosine distance, pgvector HNSW index |
| ARM1-2 | Retrieval: pure semantic search over the whole corpus, **no `cik`+year metadata pre-filter** | A pre-filter would raise recall by construction now that `DATA-5` makes that lookup reliable — but Arm 1 is the fixed baseline every later arm is compared against, and pre-filtering would change what is being measured, not just how well. Logged as a candidate variant for later, not blended into the baseline |
| ARM1-3 (open, not pursued) | BGE-M3 uses single-`[CLS]` pooling (`sentence-transformers` default), not BAAI's MCLS long-document pooling | A chunk-length slice of Arm 1's results shows a real gradient — recall@10 **0.50** short / **0.41** medium / **0.26** long — consistent with a long-document pooling weakness. Correlational, not proof: long chunks overrepresent filers hit by `CHUNK-3`'s bug, and the labeling threshold was not separately validated per length bucket. Never re-checked with `FlagEmbedding` + MCLS |
| ARM2-1 | Fusion: RRF (Cormack et al., 2009), `k=60`, top-50 from each list | Cosine similarity and BM25 scores live on unrelated, incomparable scales — summing them directly would let whichever produces bigger numbers dominate regardless of actual relevance. RRF fuses by rank instead |
| ARM3-1 | Reranker: `bge-reranker-v2-m3` (local cross-encoder) over Arm 2's fused top-50, not Qwen3-Reranker-0.6B | Checked current state (Aug 2026): Qwen3-Reranker edges out on BEIR (~59 vs ~54) but is a causal yes/no-logit architecture, so it decodes autoregressively per candidate. `bge-reranker-v2-m3` is a plain bidirectional cross-encoder — one forward pass, one score. **Our own requirement is that any nDCG gain is reported against its latency cost**, so the cleaner latency story won over the leaderboard number. Cohere Rerank (hosted) deferred to conserve free-tier call budget |
| ARM3-2 | Reranking run offloaded to Northeastern's HPC cluster (SLURM, V100 — the cluster is Explorer) via a **split-job pattern**, not laptop CPU or a live SSH tunnel | Laptop CPU swap-thrashed under normal load (~110s/query, ~25h projected). A live tunnel from the GPU node to the laptop's Postgres was rejected: a dropped connection kills the whole run, the same failure mode as the CPU run but now burning a SLURM allocation too. Split-job instead — laptop dumps a payload file, a self-contained checkpointed GPU script reranks with no DB or network dependency, laptop scores afterwards. The `xfer` host is mandatory, since the login node throttles large transfers. The full procedure and node setup are kept out of the repo, since they name cluster hosts and per-account paths; this row keeps the reasoning, which is the transferable part |
| ARM3-3 | Added cross-question batching to the HPC rerank script (20 questions' pairs per `predict()` call) | Only ~12% speedup (5.07s→4.45s) — GPU compute time, not Python call overhead, was the dominant cost, so batching could not buy the order-of-magnitude win hoped for. Adopted anyway, since it is free |

| # | decision | why |
|---|---|---|
| ARM5-1 | Arm 5 as originally scoped — BGE-M3 late-interaction / multi-vector — **dropped entirely, not built even as a pilot** | Measured against our real corpus before building anything. ## Where recall is actually lost — the company filter and the query strip

Triage, then 100 hand-read failures, then an A/B. Ordered so each row is measured before the
next is proposed. All read-only: no re-embedding, no re-index, no LLM spend.

| # | decision | why |
|---|---|---|
| RETR-3 | **The dominant failure is document selection, not chunk ranking.** Across 100 hand-read failures (300 retrieved chunks, 5 parallel analyses): 26% came from the correct filing, **50% from the right company's wrong year**, 24% from a different company | 10-Ks reprint themselves near-verbatim each year, so sibling years are equally good lexical and dense matches and RRF has no tiebreaker. | RETR-4 | **The entity wording in the question is a filter, not a search term.** 19-20 of every 20 questions name the company outright; the gold chunks say "the Company" | The questions are rewritten FinQA ("…for Philip Morris International, as reflected in the company's 2017 financial report"), so the company name and filing framing are the strongest signal reaching both retrievers — and they match every year of that issuer, and every issuer's boilerplate, equally.
